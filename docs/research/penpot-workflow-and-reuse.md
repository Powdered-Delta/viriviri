# Penpot 工作流：连接踩坑总结 与 复用性分析

本文回答两个问题：

1. **用 MCP 连 Penpot 这件事，踩过哪些坑？**（连接/操作层，可复用的经验）
2. **这套工作流能复用吗？** —— 用于「二开本项目的布局」，或「基于本项目的组件方案做别的东西」。

逐条坑的完整清单在 [penpot-mcp-authoring-pitfalls.md](penpot-mcp-authoring-pitfalls.md)（445 行，25 条）。
**本文只做汇总、提炼可复用部分、并给出复用路径与缺口**。

---

## 第一部分 · 连接与操作踩坑汇总

### 1.1 链路全貌

```text
Penpot 前端 (<你的 Penpot 主机>)
   │  ① 浏览器里打开插件 UI → Connect（用 userToken 建 WebSocket）
   ▼
MCP 服务器  <MCP 路径>?userToken=…
   │  ② MCP 协议：initialize → tools/call execute_code / export_shape
   ▼
调用方：curl / PowerShell（本仓库做法）
```

> 具体的**端点、路径与 token** 不写进提交范围内的文档，
> 只保留在本地排除文件 `docs/penpot-mcp-connection.md`（`git check-ignore` 确认排除）。

**两段 token 必须一致**：MCP URL 的 query + 插件的 WebSocket。任一缺失/不一致 →
`No userToken found…` 或 `No Penpot instance connected…`。

### 1.2 坑位索引（按"你会在哪一步撞上"排）

| 阶段 | 坑 | 一句话对策 |
| --- | --- | --- |
| **连接** | 插件离线（`No Penpot instance connected`） | 点顶栏 **MCP 胶囊** → 「在此连接」→ **白灯**；本机 4400–4403 不用起、插件按浏览器保存、公网无 manifest |
| **连接** | 点完连接**仍是离线** | 脚本 `process.exit` 关掉浏览器 → 插件随之断。必须把浏览器跑成**常驻任务**（#23） |
| **连接** | 间歇 `no heartbeat for Ns` | 标签页节流；循环重试即可，**不等于**断线 |
| **连接** | `frozen by the browser` | 标签页被挂起；重试无效，需人工唤醒或重建常驻浏览器 |
| **调用** | 偶发 `Possible HTML comment rejected (SES_HTML_COMMENT_REJECTED)` | 源码里**不要出现 `-->`**（连字符串里也不行），用 `→` |
| **调用** | `Cannot set properties of null` | `createText('')` 返回 `null` → 建文本前判空 |
| **写图形** | 图形建到**错误的板/页** | `shape.x/y` 是**页面绝对坐标**；且 `openPage()` **同一次调用内不同步**。切页单独一次调用 + 探针确认落点 |
| **写图形** | 跨页搬运报 `Cannot modify a page that is not currently active` | 不要搬运，**在新页重建** |
| **写图形** | 设 `shape.width` 报 `has only a getter` | 尺寸用 **`resize(w,h)`**，不要赋值 |
| **写图形** | 用 `!==` 比较两个 shape/flow **永不相等** | Penpot 的 proxy **不是同一性稳定的**，一律按 `id` 比 |
| **写图形** | 看似"某 API 不存在" | plugin proxy **不枚举方法** → 反射探测不到；**以 `penpot_api_info` 文档为准** |
| **画线稿** | 缩小后整块板是"黑的/空的" | 骨架以**可读性优先**：明度拉开、描边 ≥10px、字号 ≥44px；重合层用嵌套尺寸 |
| **画线稿** | 内容都在模型里、画面上却没有 | 子节点坐标落到了板外被裁掉（**x/y 是绝对坐标**） |
| **复核** | 导出 PNG 只有板背景色 | 曾误判为"导出不渲染子节点"，真因是**坐标错位**；修坐标后 1 色 → 139 色 |
| **复核** | 截图与 MCP 读回**不一致** | 插件改动会落盘但**渲染可能滞后**：先做一次无关改动触发提交再复核；**也要先怀疑自己读错图** |
| **复核** | 查看器里点击**完全没反应** | 默认 100% 缩放，目标在屏幕外 → 先按 **`F`** 适合 |
| **复核** | 按 `F` 后第一次点击仍无效 | 缩放动画未稳定，等 **≥2.5s** |
| **原型** | 想"播放"原型 | 预览是**独立页面** `#/view?…&section=interactions&index=N`；`index` 与图层序**倒序**；编辑器里按 **`G V`** 打开 |
| **原型** | 造互动 | `shape.addInteraction('click', {type:'navigate-to', destination: board})`；`interactions` 只读，用 `addInteraction`/`removeInteraction` |

### 1.3 三条方法论（比具体坑更值钱）

1. **浏览器截图是 ground truth，MCP 读回只是数据。** 两者不一致时：先想"渲染滞后"，
   再想"我是不是读错了图"（33% 缩放下标签只有 ~13px），最后才是真的数据不一致。
2. **改写前先列出全部命中项。** 我做过一次"按子串无条件改写"，把图例里一行索引文字整行覆盖掉了。
   正确做法：先把 `(板, 形状名, 原文)` 全部打印出来确认，再执行替换。
3. **脚本要幂等。** 失败会留下半成品（Penpot 不回滚）；开头按名字前缀清理自建产物，
   数值修正按"目标值 - 当前值"算 delta，已经是目标值就跳过。

## 第二部分 · 复用性分析

先给结论，再给依据与缺口。

| 复用场景 | 可行性 | 主要缺口 |
| --- | --- | --- |
| **A. 二开本项目的布局**（主题作者在 Penpot 改版式 → 落到应用） | **高**（链路大半已通） | ① 缺 `Penpot → theme.json` 的**发射器**；② **`theme.json` 目前与实现不符**（见 2.3），必须先修 |
| **B. 基于本项目组件方案做别的东西**（把组件契约当设计系统复用） | **中**（契约层可复用，组件层不可） | 组件是 B 站语义专用；跨项目复用要重定义 `ThemeCatalogs` |
| **C. 把这套 Penpot↔代码管线当通用工具** | **高**（与项目无关） | 需把"dp + quad + 元素命名"这套约定文档化并抽出脚本 |

### 2.1 现在已经具备什么（可复用的资产）

| 资产 | 位置 | 复用价值 |
| --- | --- | --- |
| **组件目录**（40+ 组件：id / 内容 / 数据绑定 / 状态 / 实例约束 / 当前所属面板） | [interaction-skeleton/README.md](../prototypes/interaction-skeleton/README.md) §3.0 | **这是复用面最大的东西** —— 独立于 Penpot，是"这个 UI 由哪些可组合单元构成"的权威清单 |
| **组合规则 5 条**（面板=组合声明；组合必须声明式；槽位关系属组合层…） | 同上 §3.0.1 | 换实现（Penpot→代码→别的设计工具）时规则不变 |
| **面板线稿（真实 dp + 真实组件 id）** | [panel-wireframes.md](../prototypes/interaction-skeleton/panel-wireframes.md) + Penpot `W1–W8` | 既是设计稿也是布局规格；元素名 = 实现 id，可机械对照 |
| **主题契约 schema**（`panels` / `slotBindings` / `layouts` / `toolbarModules` / `grabGroups` / `danmakuGroups` / `componentGroups`） | `spatial-workbench-core/.../ThemeSchema.kt`、`themes/cinema/theme.json` | **二开的正式接口**；已有 validator（error/warning 分级） |
| **锚点/偏移语义契约**（旋转序 Yaw→Pitch→Roll、`inverse(parent)×anchor×offset`、reparent 不跳变、theme-static 与 user-runtime 字段不共用） | `ThemeGeometry.kt` | 任何"声明式布局"方案都要回答这几个问题，这份契约可直接抄 |
| **提取器** `extract-panels.ps1` | 仓库外 `_refs/penpot-e2e/` | Penpot → JSON（8 面板/61 元素，dp **精确往返**） |
| **对账器** `diff-panels.mjs` | 同上 | 设计与代码的四级对账（见 2.2） |
| **常驻连接** `keepalive.mjs` | 同上 | 脚本自己把插件连接建起来并保持 |

### 2.2 对账器已经能发现什么（Tier 1–4，实测）

| Tier | 对比 | 实测结果 |
| --- | --- | --- |
| 1 | 面板 **quad / dp 画布 / 宽高比** | **3 处不一致**：`grab_handle` −26.9%、`right_rail` −22.4%、`global header` −1.7% |
| 2 | **XML 元素尺寸**（id 与设计稿同名时） | `controls.xml` 7 个按钮 `56×44` ✅；能区分「固定 dp / 权重填充 / 内容决定」三态 |
| 3 | Compose 面板 | 不可机械对账（6 个），以快照为**目标值**人工核对 |
| 4 | **`theme.json` vs 代码** | **3 处不一致 + 3 个契约有代码无**（见 2.3） |

### 2.3 ⚠️ 复用场景 A 的**前置阻断项**：`theme.json` 与实现不符

| theme.json 面板 | `sizeMeters` | 真实实现 quad | 偏差 |
| --- | --- | --- | --- |
| `mediaStage` | 1.6 × 0.9 | 1.6 × 0.9 | ✅ |
| `centerContent` | 1.5 × 1.2 | 1.5 × 1.2 | ✅ |
| `leftDetailRail` / `rightContextRail` | 0.7 × 0.9 | 0.7 × 0.9 | ✅ |
| **`transport`** | **0.9 × 0.24** | **1.32 × 0.38** | ❌ 代码大 47% / 58% |
| **`systemToolbar`** | **0.48 × 0.16** | **1.24 × 0.30** | ❌ **代码大 158% / 88%** |
| **`inputConsole`** | **0.58 × 0.42** | **1.62 × 0.68** | ❌ **代码大 179% / 62%** |
| `focusPanel` / `shorts*Rail` | 1.5×1.0 / 0.68×1.1 | **未实现** | ⚠️ 契约有、代码无 |

**这为什么是阻断项**：主题作者（二开）会**以契约为起点**写自己的 `theme.json`。
如果契约里的 `transport` 是 `0.9 × 0.24` 而真实渲染是 `1.32 × 0.38`，
作者的版式会在真机上**以完全不同的比例**出现，而且**看起来像他自己的错**。

**结论：在开放二开之前，必须先把 `theme.json` 对齐实现（或反过来，把实现对齐契约并明确宣告那是目标）。**
这是一次产品决策，不是纯技术清理 —— 需要回答"契约是描述现状，还是描述目标"。

### 2.4 场景 A 的实现路径（Penpot → 应用）

```text
① 画      Penpot W 板按约定画：元素名 = 组件 id；标注 dp 画布 / quad / z / pitch / yaw
② 提取    extract-panels.ps1  →  panel-snapshot.json（dp 已精确）
③ 发射    【缺】snapshot → theme.json（映射见下表）
④ 校验    已有 ThemeValidator（error/warning 分级）—— 发射器产物直接喂进去
⑤ 应用    已有主题运行时（presentationPolicies / slotBindings / layouts）
```

**③ 的映射关系（绝大部分是 1:1）**：

| Penpot 板上的标注 | `theme.json` 字段 |
| --- | --- |
| `quad 1.50 x 1.20 m` | `panels.<k>.sizeMeters` |
| `z -0.52` | `panels.<k>.offsetMeters.z` |
| `pitch 20` / `yaw ±45` | `panels.<k>.rotationDegrees` |
| 板名 / 元素名前缀 | `panels.<k>` 键与 `panels.<k>.component` |
| 面板的父/锚 | `panels.<k>.parent` / `.anchor` |
| 可见性策略文本 | `presentationPolicies` |
| 抓取组 / 弹幕组板块 | `grabGroups` / `danmakuGroups` |

**③ 的真正难点不在字段映射**，而在**语义**：小组件（按钮、列表项）**不**进 `panels`，
它们属于 `componentGroups` / `rootComponent` 的组件树；Penpot 板上现在只画了面板级几何
与**组件占位**，还没有"组件树"的可机读表达。**这是发射器需要先补的一层标注约定。**

### 2.5 场景 B：组件方案跨项目复用

**可复用的**：契约形状本身 ——

- `PanelClass`（`UI_PANEL` / `SCENE_PANEL` / `MEDIA_SURFACE`）× 受控路径的划分；
- `SlotSharePolicy.MIRRORED` 这类"一槽多面板"的显式声明；
- `themeableGeometry` —— **逐字段声明"主题能改什么"**，这个设计很值得抄；
- 校验分级（`validate()` 只返回 error，`inspect()` 追加 warning）；
- 纯 Kotlin 契约模块（`:spatial-workbench-core`，无 Android 依赖，JUnit 可测）。

**不可复用的**：组件目录本身是**B 站语义**（合集 / 播放列表 / 弹幕 / 投币…）。
跨项目复用得先把 `ThemeCatalogs` 的受控组件集重定义一遍。

### 2.6 场景 C：管线当通用工具

**与项目无关的部分**：Penpot MCP 的连接/读写/导出/互动、Playwright 复核、查看器实测、
提取器与对账器的**框架**（Tier 分级 + 三态判定 + 幂等改写）。

**与项目相关的部分**：只有一条约定 —— **"元素名 = 目标系统的标识符；标注里带真实单位几何"**。
这条约定是整条链路能机械对账的前提，任何项目都可以采用。

**缺口**：目前脚本散在仓库外、没有打包、没有 README、只有"约定"写在本文档里。
要当通用工具用，需要：脚本入一个独立 repo（或 `tools/`）、约定文档化、加一个 `--help`。

### 2.7 比例体系与「参考物」（**组件库的前置设计**）

> 本节来自一条实测反馈：**组件尺寸应按比例换算，不要强制 1:1 像素级对齐** ——
> 否则开发者很难掌控大小比例，也说不清"这个按钮应该是那个的两倍"。

#### 2.7.1 为什么绝对 dp 对账是错的判据

对账器第一版把 `56dp == 56dp` 判为唯一正确。这有三个问题：

1. **单位绑架**：dp 只在"某个特定面板画布"里才有意义。同一个组件换一个面板画布，
   绝对 dp 必然变；
2. **意图表达错位**：设计真正要说的是"主按钮是次按钮的 1.5 倍"，而不是"主按钮 84dp"；
3. **开发者难以掌控**：要求作者记住并精确复现每个绝对 dp，等于让他在没有比例参考的情况下手调。

**已修正**：对账器现在**主判据是比例**（元素占本面板画布的比例），
绝对 dp 差异降级为参考信息 `Δdp`，容差 ±3%。
`wrap_content` / `match_parent` 标为「内容决定，不参与比例判定」，`0dp + weight` 标为「权重填充」。

#### 2.7.2 两个比例层级（缺一不可）

| 层级 | 比例 | 表达什么 | 谁提供 |
| --- | --- | --- | --- |
| **面板内** | `元素 dp / 面板 dp 画布` | 面板内部的排版比例（按钮占多宽、列表项多高） | 面板的 `DpDisplayOptions` |
| **跨面板** | `面板 quad / 参考物` | 面板之间的物理比例（transport 是舞台的 82%） | **参考物** |

**面板内比例无法表达跨面板关系**：dp 画布只描述"面板内部的分辨率"，
两个面板各自 460×132 与 768×615 的 dp 画布之间**没有任何可比性**。
跨面板比较必须落到**米**，而米必须有一个**锚**。

#### 2.7.3 参考物规格（**已在 `handmade （复制）` 落地**）

```text
参考物 Reference Object
  图层名      @ref-base              ← ⚠️ 不要用 "/"，Penpot 会改写（见 pitfalls #26）
  视觉标签    @ref/base（写在板内文字里，只是给人看的）
  真实尺寸    1.00 m × 1.00 m        ← 正方形，任意方向换算一致
  图内内容    外框 + 0.1 m 网格（10×10）+ 0.5 m 中心十字 + 换算规则说明
  机器可读    pluginData（写在形状自身）：
                ref        = base
                meters     = 1.0,1.0
                pxPerMeter = 1000
  放置        页面左上角、所有板之外（x = −4200），不隶属任何面板、不参与原型
```

**实测落地**：Penpot 板 `@ref-base`（1600 × 1780 px），方板 1000 × 1000 px，
导出核验尺寸与网格均正确。读取方式：`board.getPluginData('pxPerMeter')`。

**换算规则**：

```text
metersPerPx   = ref.meters / ref.px
元素米数       = 元素px × metersPerPx              ← 跨面板比例
元素面板内比例  = 元素dp / 面板dp画布               ← 面板内比例
```

**为什么用 1 m 方板而不是"拿舞台当参考"**：舞台尺寸本身可能被主题改（`mediaStage.sizeMeters`
在 `themeableGeometry` 里），拿它当锚会让"锚随被测物变化"。参考物必须**不可主题化**。

#### 2.7.4 组件库该怎么表达尺寸

推荐：**组件带绝对 dp，但必须同时声明"设计基准画布"** —— 二者合起来就是一个比例。

```jsonc
// 组件清单里的一个条目
{
  "id": "transport.button",
  "size": { "w": 56, "h": 44 },
  "designedAgainst": { "canvas": { "w": 460, "h": 132 } },   // ← 比例的分母
  "ratio": { "w": 0.1217, "h": 0.3333 }                       // ← 可机械推导
}
```

**这样三方都能用**：

- **作者**：看到的是 `0.12 × 0.33`（占面板），换画布时按比例缩放，不必重算 dp；
- **对账器**：比 `ratio`，容差 ±3%，不因画布不同而误报；
- **代码**：仍然写固定 dp（Android/Compose 的天然单位），由"基准画布"保证比例不变。

#### 2.7.5 对"独立仓库"的具体建议

拆出「组件库 + Penpot 工作流」独立仓库时，**项目初始化**应至少产出：

| 产出 | 作用 |
| --- | --- |
| `@ref/base` 参考物（1 m 方板 + 网格） | 跨面板比例的锚；保证不同项目/不同作者量出来可比 |
| 一个**基准画布表**（每个面板的 dp 画布 + quad） | 面板内比例的分母；也是 `designedAgainst` 的取值来源 |
| 每个组件的 `ratio` 字段（可推导） | 让作者按比例选型，而不是抄 dp |
| 一个**比例检查器**（本仓库的对账器 Tier 2 可复用） | 在作者提交前就报"比例偏差超容差" |
| 一条约定：**元素名 = 目标系统标识符** | 机械对账的前提（见 2.6） |

#### 2.7.6 载体选择：**模板文件** vs **共享库**（已实测）

Penpot 侧的能力实测（文件卡片右键菜单 + 仪表盘）：

| 动作 | 入口 | 结果 |
| --- | --- | --- |
| **复制文件** | 文件卡片右键 → `复制` | ✅ 实测生成 `handmade （复制） （复制）` |
| **新建文件** | 仪表盘 `add-file-btn` | ✅ 实测直接进入新文件工作区 |
| **新建项目** | 仪表盘 `+ 新项目` | 存在（未点击） |
| **添加为共享库** | 文件卡片右键 → `添加为共享库` | 存在 |
| **整文件导出** | 文件卡片右键 → `下载 Penpot 文件（.penpot）` | 存在 |

**结论：初始化不该只有"复制模板"一种做法，两件事应该分开。**

| 内容 | 载体 | 为什么 |
| --- | --- | --- |
| `@ref/base` 参考物、**基准画布表**、命名约定说明 | **模板文件**（复制即得） | 这些是**页面级**产物，必须存在于每个文件里；共享库不共享页面 |
| 按钮 / 列表项 / 图标等**组件** | **共享库**（`添加为共享库`） | 库的本质是"跨文件复用、改一处全项目更新"；复制模板做不到这一点 |

> **关键区别**：复制模板是**一次性快照** —— 之后组件改进不会传播到已有文件；
> 共享库是**活的引用** —— 改库即改所有引用方。
> 因此**组件进库、锚点进模板**。

**插件 API 不能做这些**：Penpot 插件是**文件作用域**的（`penpot.currentFile` /
`createPage()`），文件的新建与复制是**仪表盘**动作，不在插件能力范围内。
所以「批量初始化若干项目文件」只能走 UI / HTTP API，不能走 MCP 插件。

## 第三部分 · 建议的落地顺序

| 顺序 | 事项 | 为什么这个顺序 |
| --- | --- | --- |
| 1 | **对齐 `theme.json` 与实现**（2.3） | 不做这步，二开一上手就被误导；且这是**产品决策**（契约=现状 or 目标） |
| 2 | 修 3 处 **dp 画布宽高比**缺陷（Tier 1） | 纯实现缺陷，已机械确诊；右 rail 若不修，新内容排版一直受挤压 |
| 3 | **建立比例体系**：加 `@ref/base` 参考物 + 每面板的基准画布表（2.7） | 这是"组件按比例"的锚；没有它，作者只能抄绝对 dp |
| 4 | 定义**组件树的可机读标注约定**（2.4 末尾） | 发射器的前置条件；否则只能生成面板级几何，生成不了组件树 |
| 5 | 写**发射器** snapshot → `theme.json` | 有了 1+3+4 才有意义 |
| 6 | 把脚本与约定**打包成可复用工具**（2.6 / 2.7.5） | 前五步稳定后再抽成独立仓库 |

**当前不应做的事**：在 1、3、4 解决之前就把 Penpot 当"二开的正式入口"对外宣告 ——
那样作者产出的主题会在真机上呈现与设计不同的比例，而原因在契约本身。

## 附 · 对账器的判据演进（一次被纠正的设计错误）

| 版本 | 判据 | 问题 |
| --- | --- | --- |
| v1 | **绝对 dp 逐值相等**（±1dp） | 把 `seek_bar` 的 `0dp + weight` 误判为不一致；更根本的是**用错了判据** —— 组件库表达的是比例，不是绝对值 |
| v2 | 三态：固定 dp / 权重填充 / 内容决定 | 修掉了假阳性，但仍是绝对判据 |
| **v3（当前）** | **比例为主判据**（`元素dp / 面板dp画布`，容差 ±3%），绝对 dp 差异降级为参考列 `Δdp` | 与"组件按比例"的设计意图一致；换画布不会误报 |

这说明**对账器本身的设计要服从组件库的语义** —— 判据选错，工具会持续产生误导性的红灯。
